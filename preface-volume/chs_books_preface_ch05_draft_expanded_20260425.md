# 总序卷第5章 Agent、Skill 与工作代理

**作者：Manus AI**  
**日期：2026-04-25**

## 本章导言

第4章已经完成了一个关键过渡：我们不再把 AI 写成单一能力块，而是将其区分为负责机理、边界、约束与可验证性的**物理 AI**，以及负责解释、推理、规划、工具调用与协同组织的**认知 AI**。但认知 AI 仍然只是一个能力描述。真正进入工程与平台层面时，还需要进一步回答：这些能力究竟由什么形式来组织、承载并对用户呈现？如果这一层没有被说清，所谓认知 AI 仍然可能只是一个概念集合，无法进入工作现场。[1] [2] [3]

因此，第5章的任务，是把认知 AI 从“能力层”推进到“执行组织层”。本章将论证：**Agent** 是认知执行层的一种组织形式，**Skill** 是其中可组合、可调用、可治理的执行单元，而**工作代理**则是把 Agent、Skill、Tool、Workflow 与审查交付链组织成统一入口的产品化形态。[1] [2] [3] 也就是说，本章的重点不是介绍几个流行术语，而是要解释它们在 CHS 体系中的准确位置。

这一区分尤其重要。因为如果把 Agent 直接写成“更聪明的模型”，它就会漂浮在平台结构之外；如果把 Skill 写成“能力标签”，它就无法承担执行单元的责任；如果把工作代理理解为聊天机器人界面的升级版，它就会错过真正的工程目标——即为用户提供一个能够调度整套能力体系的统一工作入口。[2]

从全书推进逻辑看，第5章也是一个关键转折点。前文完成的是“对象—框架—方法”的三级铺垫，而本章开始处理“执行组织”问题。也就是说，前几章回答的是系统为什么必须这样理解，而第5章开始回答系统到底如何工作。若没有这一步，双引擎将只能停留在方法口号，无法进入平台与产品层。

## 5.1 Agent 在 CHS 中不是外来物，而是认知执行层的组织形式

在流行技术叙事中，Agent 经常被描述为会思考、会调用工具、会自主完成任务的智能体。这种说法并没有错，但如果只停留在这一层，就很容易把 Agent 看成一个脱离工程体系的外来组件。对 CHS 而言，这种理解是不够的。因为在 CHS 中，任何进入运行闭环的能力，都必须说明它在感知、决策、执行、目标与边界结构中的位置。

从这一角度看，Agent 的真正意义，不是替代控制论，而是在**认知执行层**承担任务组织者的角色。相关综述表明，agent workflow 的核心并不只是生成语言，而是利用 tools、memory 与 reasoning 来完成用户定义目标，并通过 planning、execution、reflection 等阶段形成可扩展、可控制、可审查的 AI 行为框架。[1] 这一判断与本书前文提出的双引擎结构天然一致：物理 AI 负责守住底层约束，Agent 则位于认知 AI 一侧，负责任务理解、步骤规划、工具组织与反馈修订。

因此，本书中的 Agent 应被界定为：**面向目标任务、能够在认知执行链中组织工具、技能、上下文与反馈的一类认知执行体。** 它不是底层物理控制器的替身，也不是独立于系统边界之外的“外脑”，而是 Cyber 空间中一种更高层的决策组织形式。[1] [4]

这一定义带来两个直接后果。第一，Agent 的价值不在于“会说”，而在于“会组织”。它必须能够把用户目标转化为任务树、行动序列和工具链，而不是只提供单轮答案。第二，Agent 的权限并非天然无限，它的建议、调用和执行都必须接受第4章所建立的双引擎接口与治理边界约束。也就是说，Agent 可以提出行动链，但并不自动拥有越过物理 AI 或安全包络的权力。[4] [5]

## 5.2 Skill 不是能力口号，而是可组合的执行单元

如果说 Agent 是组织者，那么 Skill 就是它组织时最关键的中间层。在很多产品表述里，“技能”常常被泛化为一种营销性词汇，仿佛只要给模型冠以若干能力标签，就已经拥有 Skill 体系。CHS 不接受这种模糊写法。在本书语境中，Skill 必须是**可调用、可组合、可治理、可替换的执行单元**，它应当处在 Tool 与 Agent 之间，承担对底层能力的结构化封装。[2] [3]

HydroMind Studio 总体架构方案明确提出，产品必须深度融合 agent、skill、MCP、模型算法与 workflow，同时保留可替换、可扩展、可治理的开放面。[2] 这一表述的真正含义是：Skill 既不是最底层的原子工具，也不是最上层的任务组织者，而是把若干工具、规则、模型和上下文打包为一段**可重复执行的专业动作**。HydroClaw 的产品材料也进一步给出一个清楚的层次：L2 是 MCP Tools Layer，L3 是 Skills Layer，L4 是 Agents Layer。[3] 这说明 Skill 的角色恰恰是连接底层能力与高层任务组织的桥梁。

在水系统场景中，这一层尤其重要。因为许多关键动作并不是单次工具调用可以完成的。例如，“生成防洪会商报告”不是一个工具，“检查调度方案是否合规”也不是一个工具，“基于实测与预测生成异常处置建议”更不是单个按钮。它们往往需要组合数据检索、模型运行、规则核验、文本归纳、格式化输出等多个步骤。只有当这些步骤被封装为 Skill，Agent 才能以稳定、可治理的方式调用它们。

表 5-1 给出本书对 Tool、Skill 与 Agent 的基本区分。

| 层级 | 主要角色 | 典型功能 | 在 CHS 中的位置 |
|---|---|---|---|
| Tool | 原子能力提供者 | 检索、计算、制图、查询、模型运行 | 底层可调用资源 |
| Skill | 可组合执行单元 | 把多个工具与规则封装为稳定动作 | Agent 的专业动作接口 |
| Agent | 任务组织者 | 目标理解、步骤规划、Skill 编排、反馈修订 | 认知执行层组织体 |

由此可见，Skill 的存在价值在于让系统不必每次从最底层开始重新拼装执行链，而能够以较高抽象层复用专业动作。这一点对规模化部署尤其关键，因为只有 Skill 被结构化定义后，权限、版本、审查、替换与复用才有可能进入统一治理。

## 5.3 为什么平台入口必须是工作代理，而不是聊天界面

在很多大模型产品中，用户看到的第一入口是对话框。这种入口适合做问答、探索和单轮交互，但对复杂工程任务而言，它并不构成真正的工作入口。因为工程任务不是一句话完成的，而是要经历目标澄清、信息收集、工具执行、结果校核、审查留痕和交付收口等连续步骤。若平台仍然把自己理解为“更专业的聊天机器人”，它就很难承接从理解到交付的完整链条。

HydroMind Studio 总体架构方案对此给出了极其清晰的判断：它的目标不是“给用户更多工具”，而是“给用户一个能调度整套体系的工作代理”。[2] 这一表述之所以重要，是因为它第一次把平台入口从“工具聚合器”提升为“工作组织者”。换言之，平台的核心不在于列出多少算法、多少模型、多少菜单，而在于是否存在一个能够代表用户理解任务、调度能力、组织工作面和管理执行上下文的统一入口。

工作代理与聊天式智能的差别，至少体现在三个方面。第一，聊天式智能主要围绕一次回答展开，而工作代理围绕**任务生命周期**展开。第二，聊天式智能通常把工具调用视为辅助功能，而工作代理把 Tool、Skill、Workflow、审查与交付都视为其内在组成部分。第三，聊天式智能往往只管理对话上下文，而工作代理必须同时管理项目、任务、会话、artifact、checkpoint、approval 等多种工作对象。[2]

这正是为什么 Studio 架构强调统一产品壳、统一执行内核、统一扩展标准和多角色主智能体。[2] 在这种设计里，工作代理不再只是回答问题的人机接口，而成为用户在整套能力体系中的“代行者”。它负责代表用户进入任务现场，但又不能越过治理边界独自行使最终裁决权。

## 5.4 Agent、Skill、Workflow 与工作台应被写成同一条执行链

为了避免概念堆叠，本章必须把 Agent、Skill、Workflow 与工作台写成一条连续执行链，而不是四个并列名词。其基本逻辑可以概括为：**用户目标进入工作台，由工作代理承接；工作代理以 Agent 形式组织任务；Agent 通过调用 Skill 执行专业动作；Skill 再进一步调度 Tool、模型、知识与规则；整个过程被 Workflow 编排、被审查节点约束，并以 artifact 和交付物收口。**

这一链条并不是抽象想象，而是与既有架构材料高度一致。HydroClaw 材料中的 IntentRouter 和 AgentCoordinator 表明，Agent 不是孤立执行，而是要经过意图路由和协同组织。[3] Studio 架构中的 Project、Task、Step、Artifact、Checkpoint、Approval、ToolInvocation 等统一对象，则说明工作代理面对的不是一串聊天消息，而是一套可追踪的工作状态体系。[2]

为了使这一链条更清楚，表 5-2 对其进行压缩表达。

| 环节 | 主要对象 | 作用 | 典型输出 |
|---|---|---|---|
| 入口层 | 工作代理 / 工作台 | 承接用户目标与任务上下文 | 任务、项目、会话 |
| 组织层 | Agent | 理解目标、拆解步骤、选择 Skill | 任务树、行动计划、调用请求 |
| 执行层 | Skill | 组合工具、规则与模型形成专业动作 | 检索结果、分析结果、草稿、校核意见 |
| 资源层 | Tool / 模型 / MCP / 知识库 | 提供原子能力与数据支持 | 数据、图件、模拟结果、文档片段 |
| 编排与治理层 | Workflow / Approval / Checkpoint | 控制顺序、审查、回退与留痕 | 状态更新、审批记录、交付链 |

当这条链成立时，所谓工作代理就不再是玄学概念，而成为一个可设计、可实现、可治理的系统对象。平台的真正价值，正是在于把这些环节组织为一个统一工作面，而不是让用户自己在各种工具之间来回跳转。

## 5.5 一个典型示例：从“请生成会商材料”到完整工作链

为了避免第5章停留在概念辨析，这里给出一个贴近书稿语境的典型示例。假设用户向系统提出一个目标：“请为明天上午的防洪会商准备材料，并给出两套可行调度建议。” 若平台只是聊天界面，它最可能做的是直接输出一段文本，最多附带一些简短说明。但若平台被组织为工作代理，这个目标会触发一条完整工作链。

首先，工作代理把自然语言目标转写为任务对象，识别出其包含的信息收集、方案比较、规程校核和交付打包四类子任务。随后，Agent 将任务拆分为若干步骤，例如检索最新水情与预报、调用物理模型生成不同工况预测、调用规程核验 Skill 检查可行性、整理关键图表并生成简报草稿。每一步并不直接触达底层工具，而是通过 Skill 调用专业动作单元，以保证输出结构稳定、边界明确、日志可追踪。

在执行过程中，Workflow 负责管理阶段顺序、异常分支和审批节点。例如，当模型运行结果显示某方案存在下游超限风险时，Agent 必须将该候选方案标记为高风险，并要求重新规划；若用户身份不足以直接查看某类敏感数据，则系统在权限层即阻断相关调用。这时，工作代理不只是“回答问题”，而是在组织一条包含目标澄清、任务拆解、专业执行、校核反馈和交付收口的完整工作链。

这个示例表明，Agent、Skill 与工作代理的意义不在于提供更多术语，而在于把认知 AI 写成真实可工作的系统入口。没有这条链，AI 只能是帮助写字的助手；有了这条链，AI 才可能成为工程现场中的工作组织者。

## 5.6 Agent 如何与物理 AI 协同而不越界

由于 Agent 位于认知执行层，很容易产生一种误解：既然它能规划、调用工具、组织执行，是不是就应当直接接管系统？本书的回答是否定的。第4章已经明确，认知 AI 的建议只有在满足安全包络与运行设计域约束时，才能进入执行链；否则必须回退到物理 AI 支持的基线策略。[4] Agent 作为认知执行层的组织形式，自然也必须服从这一逻辑。

换言之，Agent 的强大不在于越权，而在于**在边界内组织复杂任务**。它可以理解规程、拆解任务、路由 Skill、组织多角色协同、生成解释和整理交付，但它不能绕过物理 AI 去直接宣布某个动作必然可执行。凡是涉及物理状态演化、安全边界判断、设备约束检验和运行级授权的地方，都必须回到物理 AI 与治理体系中完成闭合。[4] [5]

这也解释了为什么工作代理比单纯聊天式 Agent 更适合进入工程现场。前者从设计上就需要面对 approval、checkpoint 和校核回路；后者则往往默认以“回答越完整越好”为目标。对于水系统运行而言，真正有价值的不是一个总能给出答案的智能体，而是一个知道何时该建议、何时该求证、何时该等待批准、何时必须交还裁决权的工作代理。

表 5-3 对比了“聊天式 Agent”与“工作代理式 Agent”的不同定位。

| 维度 | 聊天式 Agent | 工作代理式 Agent |
|---|---|---|
| 主要目标 | 生成回答 | 组织任务并推动交付 |
| 上下文对象 | 对话历史 | 项目、任务、步骤、产物、审批 |
| 工具角色 | 可选增强功能 | 执行链内在组成部分 |
| 治理要求 | 较弱 | 强调权限、留痕、审查、回退 |
| 与物理 AI 关系 | 常被忽略 | 必须服从双引擎校验关系 |

## 5.7 为什么 Skill 体系决定平台是否能形成真正的专业化能力

在书稿扩写层面，还必须把 Skill 的战略意义说得更透。因为很多系统虽然也声称支持 Skill，但其“技能”实际上只是提示词模板或若干可选按钮，无法承担专业化能力中间层的责任。对 CHS 而言，真正的 Skill 体系至少应满足四项要求。

第一，**结构稳定**。同一 Skill 的输入输出边界应清晰、版本可控，不能每次调用都临时变化。第二，**组合友好**。Skill 必须可被更高层 Agent 组合调用，能够进入任务图与工作流，而不是一次性小脚本。第三，**治理可达**。Skill 应具有权限边界、日志记录和审查接口，以便进入行业级运行体系。第四，**领域可复用**。Skill 必须能把水系统领域中的规程核验、工况分析、方案生成、报告整理等重复动作固化为稳定专业动作。

如果没有这样的 Skill 体系，平台会很快走向两个极端：要么一切都被压回底层工具，导致用户必须自己拼装执行链；要么一切都被塞进大模型提示词，导致执行链不可审计、不可替换、不可验证。前者无法形成产品化入口，后者无法形成工程化可信度。Skill 体系恰恰是避免这两个极端的关键中间层。

## 5.8 从产品入口到学科语言：为什么第5章是平台与治理的桥梁

第5章的意义，不只在于为平台设计提供概念清单，更在于为全书建立一条新的中间层。前几章已经分别说明了问题背景、对象边界、框架层级和双引擎方法，但如果缺少 Agent、Skill 与工作代理这一层，那么后面的平台、协议、治理与认证章节就很难知道自己究竟在约束什么、承载什么、放权给什么。

也就是说，第5章扮演的是桥梁角色：它把第4章的“认知 AI 能力分工”进一步写成“执行组织结构”，从而使第6章关于 WNAL、ODD、xIL 与安全包络的治理对象变得明确，也使后续平台章节中的 Studio、HydroOS、HydroMAS、contracts 与工作台不再只是技术拼图，而成为同一执行链上的不同层次。[2] [3] [4]

从学科语言的角度看，这一步也很重要。因为 CHS 若要成为一套真正成熟的对象语言，就不能只定义物理对象和控制结构，还必须定义在复杂运行场景中，谁来理解任务、谁来组织能力、谁来管理执行链、谁来接受治理约束。Agent、Skill 与工作代理的引入，正是对这一问题的正面回答。

## 本章小结

本章的核心工作，是把认知 AI 从抽象能力描述推进为可落地的执行组织结构。通过对 Agent、Skill 与工作代理的辨析，可以得出五个结论。

第一，Agent 在 CHS 中并不是替代控制论的外来物，而是位于认知执行层、负责任务组织与能力编排的组织形式。[1] [4] 第二，Skill 不是模糊能力标签，而是连接 Tool 与 Agent 的可组合执行单元，是权限、治理、复用与版本管理得以成立的关键中间层。[2] [3] 第三，工作代理之所以比聊天式智能更适合作为平台入口，是因为它围绕任务生命周期而不是单轮回答组织系统能力，能够承接从理解到交付的完整闭环。[2] 第四，Agent、Skill、Workflow 与工作台必须被写成同一条执行链，否则平台架构与治理体系会失去统一对象。[2] [3] 第五，Agent 的价值不在于越过边界直接接管系统，而在于在物理 AI 与治理边界之内，组织复杂任务、协调多角色动作并形成可追溯的工作流。[4] [5]

下一章将把焦点进一步推进到治理前置层，说明为什么没有运行等级、适用边界、在环验证与回退机制，就没有资格谈高等级自主运行。届时，前文所定义的工作代理，也将第一次被放回严格的授权与验证框架之中审视。
