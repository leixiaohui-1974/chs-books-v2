## 一、为什么 T5 需要 ch09（MLOps）

T5 当前 8 章覆盖了：算法选型（ch01）、预报模型（ch02）、异常检测（ch03）、视觉算法（ch04）、强化学习（ch05）、知识图谱（ch06）、网络安全（ch07）、工程案例（ch08）。

但这些章节回答的是"算法层面怎么做"——选什么模型、怎么训练、怎么调参。

工程实践中，算法工程师还面临一组完全不同性质的问题：

- 模型版本治理（v1/v2/v3 怎么管，下线策略是什么）
- 训练数据/特征/标签/模型/推理结果的可追溯性（出问题怎么回滚）
- 模型上线后的持续监控（特征漂移、性能衰减、ODD 越界）
- A/B 测试与灰度发布（怎么不让一次部署毁掉一条调水干线）
- 模型的"再训练—验证—部署"流水线自动化

这是一组**算法-工程协同**问题，T5 不补这一章就有断点：T2b 讲算法原理 → T5 ch01-08 讲算法选型与调参 → 然后呢？模型怎么进入生产、怎么持续运行、怎么退役——这些问题在 T2b/T5 ch01-08 中都没有覆盖。

T5 ch09 的使命是把"算法工程师视角的 MLOps"补上。

## 三、T5 ch09 章节大纲（10 节，目标字数 1.0—1.2 万字）

> 章名：**MLOps 与模型部署：算法到生产的工程链路**

### 9.1 为什么水利 MLOps 不同于通用 MLOps（约 1000 字）

- 通用 MLOps 假设：可频繁重训、A/B 自由切换、回滚成本低、模型故障不直接造成物理损失
- 水利 MLOps 现实：训练数据来之不易（一次洪水才一组样本）、回滚需考虑物理状态连续性、模型故障可能直接导致水位失控
- 三个根本区别：(1) 数据稀缺性 → 重训窗口长（季度而非每日）；(2) 物理后果不可逆 → 上线必须经 HIL 验证；(3) ODD 强约束 → 模型适用边界须显式声明并实时监测

### 9.2 模型版本治理与制品库（约 1500 字）

- 模型工件四元组：训练代码哈希 + 训练数据快照 + 超参数 + 模型权重——四者绑定才构成可复现的模型版本
- 制品库选型：MLflow / DVC / Weights & Biases / 自研——水利场景的合规性要求
- 版本号命名规范：major.minor.patch + 训练数据期 + WNAL 等级
- 退役策略：何时把 v1 从生产环境移除（不能立即删——审计要求保留 5 年）

### 9.3 训练流水线（Training Pipeline）（约 1500 字）

- 三段式流水线：数据准备 → 训练 → 验证
- 数据准备：DQC 接入（与 ch03 异常检测对接）、特征工程版本化、训练/验证/测试集划分的水文学考量（不能简单随机切——必须按时间或洪水事件划分以避免信息泄漏）
- 训练管道：超参搜索框架（Optuna/Ray Tune）、计算资源管理、分布式训练的工程权衡
- 验证门禁：性能阈值（如 LSTM 洪水预报 NSE > 0.85）+ ODD 内极端值表现 + 可解释性产物（特征重要性图）

### 9.4 模型 → Skill 封装（约 1200 字）

- 引用 [T4 ch03] Skill 五元组接口
- 模型作为 Skill 的封装清单：输入接口契约（特征列表+量纲）、输出接口契约（含置信度/不确定性）、ODD 声明、降级策略
- 推理框架：ONNX Runtime / TensorRT / Triton——水利场景的延迟需求
- 模型容器化：Docker 镜像的最小化与签名

### 9.5 部署：金丝雀 / 灰度 / 蓝绿（约 1200 字）

- 引用 [T4 ch12] HydroOS 部署运维框架
- 三种部署模式在水利的取舍：
  - 金丝雀：小流量切到新模型——水利场景下慎用，因为"小流量"对水网无意义
  - 灰度：按渠段/泵站分批切换——更适合水利
  - 蓝绿：双环境并行 + 一键切换——HIL 验证后的标准做法
- 上线前的强制门禁：HIL 通过 + 调度员签字 + 变更窗口

### 9.6 在线监控（Model Monitoring）（约 1500 字）

- 四类监控：
  - 输入特征漂移（KS 检验、PSI）
  - 预测分布漂移（输出范围、置信度分布）
  - 性能漂移（与水文实测的对比 RMSE）
  - ODD 状态实时监测（与 ch03 异常检测、第十章 ODD 监控统一）
- 漂移→响应的决策表：何时报警、何时回滚、何时触发再训
- 监控数据的存储：时序数据库 + 长期归档

### 9.7 模型可观测性（Observability）（约 1000 字）

- 三大可观测维度：日志、指标、追踪
- 推理追踪：每一次推理的输入/输出/中间张量是否需要保留——水利合规要求 + 存储成本权衡
- 与 [T1-CN §13.4 审计链] 的对接：模型推理事件作为审计链的一类事件
- 异常排查的工程方法：从"线上异常"到"训练数据问题"的反向追溯

### 9.8 持续训练与 ODD 演化（约 1200 字）

- 何时再训：被动触发（漂移报警）vs 主动触发（新洪水事件、新工况）
- 再训的工程流水线：与 9.3 的初次训练有何不同（增量学习 vs 全量重训）
- ODD 收缩与扩展：模型上线时 ODD 是保守的，运行积累数据后 ODD 可以扩展——但扩展须经新一轮 HIL 验证
- 与 [T1-CN §10.6 等级评估] 的对接：模型迭代如何驱动 WNAL 等级的提升

### 9.9 模型供应链安全（约 800 字）

- 第三方模型的合规审查：开源模型/购买模型的尽职调查
- 模型签名与完整性校验
- 训练数据的合法性：水文数据的版权、传感器数据的脱敏

### 9.10 工程实例：胶东调水的洪水预报模型 MLOps 实践（约 1000 字）

- 用胶东案例（与 ch08 案例一同源）演示 9.1—9.9 的具体落地
- 关键数据：模型版本数（自 2022 年累计 12 个 v）、回滚次数（3 次）、漂移事件（5 次）
- 教训：
  - 教训 1：不要把训练流水线搞得太自动化——水文数据的脏数据率高，人工 sanity check 不能省
  - 教训 2：HIL 测试床本身也需要版本管理——HIL 升级时上面运行过的所有模型验证结果都失效
  - 教训 3：ODD 收缩比扩展更频繁——真实运行总会暴露训练时未覆盖的工况
