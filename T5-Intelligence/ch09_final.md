## 9.1 为什么水利 MLOps 不同于通用 MLOps

通用 MLOps 实践（以推荐系统、广告点击率预测、客服对话为代表）建立在四个隐含假设之上：

第一，**训练数据可频繁刷新**。互联网产品每天产生 TB 级数据，模型可以每周乃至每天重训，错误模型的影响可以在下次重训时自然修复。

第二，**A/B 切换成本低**。给 5% 的用户看新模型推荐结果，效果不好就切回旧模型——用户感知很弱，业务损失有限。

第三，**回滚是无状态的**。把模型 v2 切回 v1，下一次推理立即生效，不存在"过渡状态"问题。

第四，**模型故障 = 业务损失**，但不直接造成物理损害。推荐了一个不爱看的视频，用户最多关掉应用走人。

水利场景把这四个假设全部颠覆。表 9-1 列出根本差异。

**表 9-1 通用 MLOps 与水利 MLOps 的工程现实对比**

| 维度 | 通用 MLOps | 水利 MLOps |
|------|----------|----------|
| 训练数据 | 每日新增 TB 级 | 一次极端事件（洪水/冰期）才一组样本，年增数据有限 |
| 重训窗口 | 每日—每周 | 季度—年度 |
| A/B 切换 | 5% 用户分流，无感知 | 渠段不能"分流"，调度系统必须全局一致 |
| 回滚 | 无状态切换 | 有状态：水位/闸门已被新模型动了，回滚后状态怎么办 |
| 故障后果 | 业务指标下降 | 水位失控、设备损坏、供水中断、生命财产风险 |
| 上线门禁 | 离线指标达标即可 | 必须经 HIL 验证 + 调度员签字 + 变更窗口 |
| ODD 适用边界 | 隐式（数据分布） | **显式声明**（六维 ODD 形式化定义） |

这三条根本差异——数据稀缺性、物理后果不可逆、ODD 强约束——决定了水利 MLOps 不能照抄互联网行业的最佳实践。本章后续各节将分别展开这三条差异在版本治理、训练流水线、部署模式、监控、再训等环节的具体反映。

[物理直觉] 通用 MLOps 像在互联网商场试穿衣服——不合适脱下来再换一件即可，没人受伤。水利 MLOps 像给在飞行中的飞机换发动机——动作精度要求高、操作不可逆、容错窗口窄、出错成本是机毁人亡。这不是危言耸听：2024 年某调度中心因为一次未充分验证的 LSTM 模型上线，导致下游某城市供水压力波动 4 小时，虽未造成事故，但事后追责成本远超当年的全部 ML 研发投入。

## 9.2 模型版本治理与制品库

### 9.2.1 模型工件的"四元组绑定"

一个生产环境的模型版本不是只有"模型权重文件"。要做到可复现、可审计、可回滚，必须把四个工件作为一个整体绑定起来：

$$
\text{ModelArtifact} = (h_\text{code}, \, S_\text{data}, \, \Theta_\text{hyper}, \, W_\text{weights}) \tag{9-1}
$$

其中 $h_\text{code}$ 为训练代码的 Git 提交哈希，$S_\text{data}$ 为训练数据集的 DVC 快照（含数据版本号 + 完整性哈希），$\Theta_\text{hyper}$ 为超参数集合（包括随机种子），$W_\text{weights}$ 为模型权重序列化文件（PyTorch .pt / TensorFlow SavedModel / ONNX）。

四元组缺一项就失去复现能力——这是水利场景与互联网最大差异之一：水利模型上线后可能在生产环境运行 5—10 年，工程师早已离职，原训练代码可能丢失。一旦出现"为什么 v3 不如 v2"的疑问，没有四元组绑定就无从查起。

[工程解释] 一个真实教训：胶东调水某 LSTM 预报模型在 2023 年表现良好，2024 年同一模型在新季节的预报偏差变大。复盘时发现：(1) 训练代码仓库已多次重构，原训练脚本无法直接运行；(2) 训练数据快照未保留，原始 2018—2022 数据已被新数据"覆盖"（监测站点更换、单位换算变化）；(3) 超参数只在论文里有，但论文里的随机种子写错。结果：花了 6 个月才把 v3 的复现基线建好——比原本计划的"重训 v4"还慢。

### 9.2.2 制品库选型

主流模型制品库工具对比见表 9-2。

**表 9-2 模型制品库工具对比（水利场景）**

| 工具 | 模型版本 | 数据版本 | 实验追踪 | 部署集成 | 水利适配 |
|------|--------|--------|--------|--------|--------|
| MLflow | ✅ | ⚠️ 弱 | ✅ | ✅ | 中等（需自定义元数据扩展） |
| DVC | ⚠️ 弱 | ✅ | ⚠️ 弱 | ⚠️ | 优（数据版本是水利核心需求） |
| Weights & Biases | ✅ | ⚠️ | ✅ | ⚠️ | 弱（数据出境合规问题） |
| 自研（基于 Git LFS + S3） | ✅ | ✅ | ⚠️ | 取决于实现 | 优（可定制） |

**水利场景的选型原则**：

1. **数据版本管理优先级高于实验追踪**——水利数据稀缺，每一份训练数据快照都是稀有资产
2. **不要选纯云端的 SaaS 方案（如 W&B）**——大型水利工程涉及国家关键基础设施，训练数据出境受监管限制
3. **MLflow + DVC 组合是常见的折中**——MLflow 管模型与实验，DVC 管数据，两者通过 Git 关联

### 9.2.3 版本号命名规范

水利模型版本号建议采用扩展的语义化版本：

```
{算法名}-v{major}.{minor}.{patch}+{data_period}+L{wnal}
例：lstm_inflow_forecast-v2.3.1+2018Q1-2023Q4+L2
```

- `major`: 算法架构变更（如 LSTM → Transformer）
- `minor`: 训练数据扩展（如新增一个洪水年份数据）
- `patch`: 超参数调整或 bug 修复
- `data_period`: 训练数据时间范围
- `wnal`: 该模型经过验证的最高 WNAL 等级（参考 《水控》§10.3）

WNAL 等级嵌入版本号是水利 MLOps 的特殊设计——它让运维人员一眼就能判断"这个版本能不能用在 L3 的工程"。

### 9.2.4 退役策略

模型不能"删掉就完事"。审计要求规定（参考 《标治》第 10 章 持续合规追踪），生产环境运行过的模型版本及其全部四元组必须保留至少 5 年。退役流程：

```
v1 上线 → v2 上线（v1 进入"备用回滚"状态）→ v3 上线（v1 进入"归档"状态）
v1 归档 5 年后才允许删除
```

归档不等于删除——归档存储可以使用低成本介质（对象存储冷归档层），但要保证可解归档与读取。

## 9.3 训练流水线（Training Pipeline）

水利模型训练流水线分三段：数据准备 → 训练 → 验证。

### 9.3.1 数据准备的水利特殊性

**接入 DQC**。训练数据必须先通过 《算法》第 3 章 异常检测建立的数据质量管控（DQC）流水线。常见水文数据问题：传感器漂移、阶跃跳变、冰期冻结值、雷击导致的脉冲、人工录入错误——任何一类未清洗的脏数据都可能导致模型学到错误模式。

**特征工程的版本化**。水利特征工程往往涉及水文学经验公式（如蓄满产流的初损扣除、汇流的等流时线）——这些经验公式本身有"工程师选择"成分。每一次特征工程逻辑变更都必须作为新的代码哈希提交，并触发模型重训。

**数据集划分**。这是水利与通用 ML 最大差异之一。**严禁简单随机划分**——会造成时间信息泄漏。正确做法有三种：

1. **按时间切分**：训练集 2018—2022，验证集 2023，测试集 2024。简单但样本利用率低
2. **按洪水事件切分**：训练集含历史前 80% 的洪水事件，验证集含中间 10%，测试集含最近 10%。事件级别避免数据泄漏
3. **滚动窗口**：训练集滚动前移、验证集随之滚动——更接近生产环境真实情况

公式 (9-2) 给出滚动窗口划分的形式化表达：

$$
\mathcal{D}_\text{train}^{(k)} = \{(x_t, y_t) \mid t_0 \le t \le t_0 + k \cdot \Delta T\}, \quad \mathcal{D}_\text{valid}^{(k)} = \{(x_t, y_t) \mid t_0 + k \cdot \Delta T < t \le t_0 + (k+1) \cdot \Delta T\} \tag{9-2}
$$

其中 $\Delta T$ 为窗口步长（典型值 1 年），$k$ 为窗口序号。

### 9.3.2 训练管道

超参搜索框架推荐 Optuna 或 Ray Tune——两者都支持 Bayesian 优化和早停。水利场景的特殊性：

- **超参搜索代价高**：单次训练可能跑 8—24 小时（LSTM with Attention，全国流域数据），不能像广告 CTR 那样跑几千次实验
- **建议先用 grid search 粗扫 5—10 组，再用 Bayesian 在最佳邻域细搜**

分布式训练在水利场景使用率不高——多数水利模型规模在 10M—100M 参数之间，单 GPU 即可。如使用分布式训练，注意：(1) 数据并行的 batch normalization 同步问题（不同流域数据分布差异大）；(2) 训练日志的多 worker 聚合。

### 9.3.3 验证门禁

验证不通过则模型不得进入下一步。门禁分三层：

**性能门禁**。最小阈值由项目立项时定义。例：LSTM 洪水预报，6 小时预见期 NSE > 0.85，24 小时 NSE > 0.70。

**ODD 内极端值门禁**。模型在 ODD 边界附近的表现往往恶化——必须单独测试。设计极端工况测试集（极枯/极丰/冰期/检修），全部通过后方可上线。

**可解释性产物**。模型必须输出特征重要性图、典型样本预测可视化、注意力分布（如有）。这些产物不影响精度，但缺失则下游审计不通过。

## 9.4 模型 → Skill 封装

引用 《平台》第 3 章 Skill 五元组：`Skill = (id, version, input_schema, output_schema, executor)`。

把训练好的模型封装为 Skill，需要补充水利特有的元数据：

### 9.4.1 输入接口契约

```yaml
input_schema:
  features:
    - name: rainfall_3h
      unit: mm
      range: [0, 200]
    - name: water_level_upstream
      unit: m
      range: [10.0, 35.0]
  validation:
    - rule: rainfall_3h must be DQC.passed
    - rule: water_level_upstream must be within ODD.H
```

每一个特征必须明确单位和合法范围——这是水利领域 vs 通用 ML 的关键差异。通用 ML 默认特征经过预处理，水利场景下特征的原始物理意义必须保留。

### 9.4.2 输出接口契约

```yaml
output_schema:
  prediction:
    - name: inflow_forecast_h6
      unit: m3/s
      type: distribution  # 不是点估计而是分布
  uncertainty:
    method: ensemble  # 或 dropout / quantile_regression
    confidence_band: [0.05, 0.95]
  odd_status:
    - in_odd: bool
    - dimensions_violated: list[str]
```

**输出必须包含不确定性估计**——水利下游决策需要知道"这个预报有多可靠"。常用方法：集成预报（5—10 个不同种子的模型平均 + 标准差）、Monte Carlo Dropout、分位数回归。

### 9.4.3 ODD 声明

```yaml
odd_declaration:
  H_hydrology: 来水范围 [P=5%, P=95%]
  P_physical: 闸门可用度 ≥ 80%
  D_data: 传感器在线率 ≥ 90%, 通信延迟 ≤ 2 min
  E_environment: 非冰期, 非检修期
  C_cyber: SCADA 链路正常
  G_governance: WNAL ≤ L2
```

ODD 声明是模型上线前必须提交的——也是模型在线监控的基准（见 §9.6）。

### 9.4.4 降级策略

```yaml
fallback_strategy:
  on_input_invalid: use_persistence_forecast  # 持续预报作保底
  on_inference_timeout: use_cached_forecast   # 用缓存
  on_odd_violation: trigger_takeover          # 进入 CHS 接管态（《水控》§2.7）
```

### 9.4.5 容器化与签名

模型 Skill 打包为 Docker 镜像。镜像要求：

- 基于精简基础镜像（python:3.11-slim 或 nvidia/cuda 最小化版本）
- 不包含训练代码（推理与训练分离）
- 不包含训练数据（数据通过运行时挂载）
- 镜像哈希签名（SHA-256）+ 制品库归档
- 推理框架优先级：ONNX Runtime（跨平台）> TensorRT（NVIDIA GPU 加速）> PyTorch / TensorFlow（开发期）

## 9.5 部署：金丝雀 / 灰度 / 蓝绿

引用 《平台》第 12 章 HydroOS 部署运维。水利场景的三种部署模式取舍：

### 9.5.1 金丝雀部署（Canary）：水利场景慎用

通用做法：5% 用户切到新模型，观察指标，无异常则逐步扩大。

水利场景的问题：**渠道不能"5% 分流"**。同一个调水干线只有一套水力系统，不能让 5% 的水流走 v1 模型、95% 走 v2。即使在多渠段网络中，把 5% 的渠段切到新模型也意味着这些渠段的下游决策与上游不一致——耦合系统会出问题。

**水利金丝雀的变通**：在数字孪生（影子模式）中并行运行新模型，与生产模型对比 30 天，差异符合预期再切换。本质上不是流量分流，而是"双模型推理 + 单模型执行"。

### 9.5.2 灰度部署（按渠段/泵站分批切换）

更适合水利。把工程划分为相对独立的子系统（如胶东 13 个管理站），逐站切换：

- 第 1 周：1 站切到新模型，其余 12 站维持旧模型
- 第 2—3 周：观察这 1 站的运行数据，无异常
- 第 4 周：扩大到 3 站
- ...
- 第 N 周：全线切换完成

灰度部署的关键是**站间一致性**——必须确保新旧模型在边界处的输出不会引发振荡。这需要在每次扩大灰度范围时做局部 SIL 验证。

### 9.5.3 蓝绿部署：HIL 验证后的标准做法

双环境并行：
- **蓝环境**：当前生产模型 v1 持续运行
- **绿环境**：新模型 v2 完成 HIL 验证后部署，但不接入生产数据流，只做"影子预测"
- **切换**：变更窗口内，由调度员按按钮一键将控制权从蓝切到绿

蓝绿部署的优势是回滚瞬时——出问题立即按按钮回切。代价是要双倍的硬件资源。水利的关键基础设施场景，这个代价值得付。

### 9.5.4 上线门禁清单

无论哪种模式，模型上线必须通过以下强制门禁：

**表 9-3 水利模型上线门禁清单**

| 门禁项 | 验证方式 | 通过条件 |
|------|--------|--------|
| HIL 验证 | 真实硬件 + 全工况覆盖 | 100% 通过率，无 P0/P1 缺陷 |
| ODD 边界扫描 | 极端值采样 | ODD 边界附近性能不显著恶化 |
| MRC 触发链路 | 故障注入 | MRC 触发延迟 ≤ 设计上限 |
| 调度员签字 | 行政流程 | 工程负责人 + 调度长双签 |
| 变更窗口 | 排班 | 非汛期 / 非高峰用水期 |
| 回滚预案 | 文档 + 演练 | 文档完备 + 最近一次演练在 30 天内 |

任何一项不通过即不得上线。

## 9.6 在线监控（Model Monitoring）

模型上线只是开始。生产环境的模型监控覆盖四个维度。

### 9.6.1 输入特征漂移

特征 $X$ 的训练分布与在线分布是否一致。常用统计：

**KS 检验（Kolmogorov-Smirnov）**：

$$
D_{KS} = \sup_x |F_\text{train}(x) - F_\text{online}(x)| \tag{9-3}
$$

当 $D_{KS}$ 超过阈值（典型 0.1）时报警。

**PSI（Population Stability Index）**：

$$
\text{PSI} = \sum_{i} (p_i^\text{online} - p_i^\text{train}) \cdot \ln\frac{p_i^\text{online}}{p_i^\text{train}} \tag{9-4}
$$

PSI < 0.1 稳定，0.1—0.25 中度漂移，> 0.25 严重漂移需重训。

水利场景的特殊性：**季节性漂移天然存在**——冬季水位与夏季水位分布本就不同。监控要按季节分桶比较，而非全年汇总。

### 9.6.2 预测分布漂移

模型输出 $\hat{y}$ 的分布是否与训练时的预测分布一致。包括：输出范围（最大值/最小值/分位数）、置信度分布、不确定性带宽。

异常情况：模型在生产环境输出值集中在训练分布的某一端——可能是输入漂移已经发生但未被 §9.6.1 检测到。

### 9.6.3 性能漂移

最直接的指标：与水文实测的对比 RMSE / NSE。

**滞后问题**：水文实测往往滞后 24 小时甚至更长（人工核对、设备同步延迟）。性能漂移监测必然有时滞——这是水利与互联网的根本差异（互联网点击数据实时返回，性能实时可观）。

**应对**：用"快指标"（输出分布漂移）作为性能漂移的领先指标，"慢指标"（实测对比 RMSE）作为终极判据。

### 9.6.4 ODD 状态实时监测

把 §9.4.3 的 ODD 声明转换为实时监测的判定函数：

```python
def in_odd(state):
    return all([
        state.rainfall_3h <= ODD.H_hydrology.upper,
        state.sensor_online_rate >= ODD.D_data.lower,
        state.scada_latency <= ODD.C_cyber.upper,
        ...
    ])
```

ODD 越界即触发降级——这是 《水控》§11.1 安全包络在模型层面的具体体现。

### 9.6.5 漂移→响应决策表

**表 9-4 漂移类型与响应行动决策表**

| 漂移类型 | 严重程度 | 推荐行动 | 决策权 |
|---------|--------|--------|------|
| 单特征 PSI > 0.25 | 中 | 触发再训计划 | 算法工程师 |
| 多特征 PSI > 0.25 同时漂移 | 高 | 立即灰度回滚 + 紧急再训 | 调度长 + 算法负责人 |
| 输出分布严重偏离 | 中 | 切到保守降级模式 + 调查 | 算法工程师 |
| 实测对比 RMSE 翻倍 | 高 | 立即回滚 + 启动专项分析 | 调度长 |
| ODD 越界（任一维度） | 严重 | 触发 MRC（接管态） | 自动 + 人工确认 |

## 9.7 模型可观测性（Observability）

### 9.7.1 三大维度

可观测性 = 日志 + 指标 + 追踪。三者解决不同问题：

- **日志（Logs）**：发生了什么事件
- **指标（Metrics）**：当前状态是什么样
- **追踪（Traces）**：一次请求经过了哪些环节

### 9.7.2 推理追踪的工程权衡

每一次推理是否需要保留输入/输出/中间张量？

- **完全不保留**：合规风险（事后无法追溯，无法复现）
- **完全保留**：存储爆炸（一个 LSTM 模型一天可能产生数 TB 数据）
- **常见折中**：保留输入+输出（必须），中间张量按采样策略保留（如 1%）

水利合规的硬性要求：保留至少 5 年的输入+输出（参考 《标治》第 12 章 数据治理）。中间张量是否保留由项目 WNAL 等级决定——L3 以上建议至少 5% 采样。

### 9.7.3 与审计链对接

《水控》§13.4.3 审计链记录三类事件：控制事件、状态事件、人机交互事件。模型推理事件应作为"状态事件"的一种纳入审计链：

- **事件类型**：model_inference
- **关键字段**：model_version, input_features_hash, prediction_value, confidence, odd_status, latency
- **关联**：链接到产生此推理的控制指令、推理结果对应的状态变化

审计链的 append-only + 哈希链确保推理记录不可篡改。

### 9.7.4 异常排查的反向追溯

发现线上推理异常时，反向追溯链路：

```
线上异常 → 推理日志 → 输入特征哈希 → 训练数据快照 → 训练时该特征分布 → 是否漂移
```

这条链路的每一环节都需要 §9.2 的四元组绑定支撑。**没有四元组，反向追溯就走不下去**。

## 9.8 持续训练与 ODD 演化

### 9.8.1 何时再训

**被动触发**：§9.6 监控漂移报警 → 自动启动再训流水线。

**主动触发**：

1. 新洪水事件后——新数据是宝贵的极端样本
2. 新工况发生后（新建分水口、新水源接入）——ODD 可能需要扩展
3. WNAL 等级跃迁前——L2→L3 需要通过更严格的 HIL 验证

### 9.8.2 增量学习 vs 全量重训

通用做法是增量学习（continual learning），但水利场景慎用：

- 增量学习的"灾难性遗忘"问题在小样本场景特别严重
- 对历史样本的可解释性变差（"为什么 v3 比 v2 在某个工况差"——增量学习无法回答）

**推荐做法**：水利场景以全量重训为主，增量学习仅用于"特征工程层面"的轻度调整（如新增一个传感器特征）。

### 9.8.3 ODD 收缩与扩展

模型上线时 ODD 应**保守**——只覆盖训练数据完全覆盖的工况。

随着运行积累数据，ODD 可以**扩展**——但每次扩展须经新一轮 HIL 验证。胶东调水的实践：每年扩展 ODD 一次，扩展前组织一次为期两周的 HIL 集中验证。

ODD 也可能**收缩**——当生产环境暴露训练时未覆盖的失败模式时。收缩比扩展更频繁——这是 §9.10 的胶东案例的关键教训之一。

### 9.8.4 与 WNAL 等级评估对接

《水控》§10.6 给出 WNAL 等级评估方法。模型迭代如何驱动 WNAL 等级提升：

- L1 → L2：模型能力达标 + ODD 范围达标 + 持续 6 个月稳定运行
- L2 → L3：增加完整安全包络 + xIL 验证 + MRC 触发链路 + 法规合规
- L3 → L4：增加多模型协同 + 长期稳定性证据（≥ 2 年）

模型上线后的 WNAL 评估每年组织一次，通过则进入下一等级，未通过则保持当前等级。

## 9.9 模型供应链安全

### 9.9.1 第三方模型审查

水利项目是否可以使用开源/购买的模型（如 HuggingFace 上的预训练 Transformer）？

合规审查要点：

1. **来源合法性**：模型许可证（Apache / MIT / 商用许可）是否允许在关键基础设施使用
2. **训练数据合规**：第三方模型的训练数据是否包含未经授权的水文数据
3. **后门检测**：使用 NeurIPS 2018 后门检测方法（trigger pattern detection）扫描模型权重
4. **能力测试**：在自己的水利测试集上跑一遍——开源模型的"通用能力"不等于水利适用性

### 9.9.2 模型签名与完整性

模型权重文件的 SHA-256 哈希作为版本一部分。运行时校验：

```python
def load_model(path, expected_hash):
    actual_hash = hashlib.sha256(open(path, 'rb').read()).hexdigest()
    assert actual_hash == expected_hash, "Model integrity check failed"
    return torch.load(path)
```

任何一次模型文件修改（即使是文件系统层面的位翻转）都会导致哈希不匹配——立即拒绝加载。

### 9.9.3 训练数据合法性

水利数据的版权与脱敏要求：

- 国家级监测站数据需向水利部备案后使用
- 跨流域数据共享需经省级协调
- 涉及关键工程参数（如水库坝高、库容）的数据需经审批

## 9.10 工程实例：胶东调水的洪水预报模型 MLOps 实践

### 9.10.1 系统概况

胶东调水自 2022 年起部署基于 LSTM 的入库流量预报模型，覆盖 13 个泵站上游汇水区。模型作为 Skill 接入 HydroOS（《平台》第 3 章），输出 6 小时和 24 小时预见期的入库流量预报，输入到 MPC 调度求解器。

### 9.10.2 关键数据（截至 2026 年 4 月）

**表 9-5 胶东 LSTM 入库流量预报模型 MLOps 实践数据**

| 指标 | 数值 |
|------|------|
| 累计模型版本数 | 12 个（v1.0 至 v3.2） |
| 重训次数 | 7 次（2 次主动+5 次被动） |
| 回滚次数 | 3 次 |
| 漂移报警事件 | 18 次（其中 5 次升级为回滚） |
| ODD 收缩事件 | 4 次 |
| ODD 扩展事件 | 2 次 |
| 平均上线门禁通过周期 | 17 天 |
| HIL 验证累计场景数 | 247 个 |

### 9.10.3 三个工程教训

**教训 1：训练流水线不能太自动化**

最初设计时希望 DQC + 训练 + 验证全自动，每月一次。运行半年后发现：自动化 DQC 漏过了一类"传感器在汛期被洪水淹没后报错值"的问题——这类样本同时出现在 train 和 valid 集，模型学到了"输入异常 → 输出特定大值"的伪模式，验证指标看起来正常，但生产环境碰到正常的高水位时也输出大值。

**改进**：每次训练前增加"人工 sanity check"步骤——算法工程师必须查看 DQC 报告并签字才能进入训练。代价是流水线自动化程度下降，每月节省的人力从计划的 80% 变成实际的 30%——但模型质量明显提升。

**结论**：水利数据的"脏"度高于通用场景，自动化的 DQC 不能完全替代人工审查。

**教训 2：HIL 测试床本身需要版本管理**

2024 年 HIL 测试床做了一次硬件升级（从 dSPACE SCALEXIO 升级到下一代型号）。升级后所有此前在该 HIL 上运行过的模型验证记录技术上仍然存在，但因为底层信号采样精度变化，部分边界场景的验证结果其实已经"失效"——但这一点在升级当时没有被识别出来。

3 个月后的一次复盘中发现：v2.5 模型在新 HIL 上重新跑同样的场景，结果与升级前不一致。结论：**HIL 测试床的版本变更必须触发所有在产模型的 HIL 重验证**，且 HIL 升级日志必须纳入审计链。

**教训 3：ODD 收缩比扩展更频繁**

最初预期 ODD 是单调扩展的——随着数据积累，模型适用范围越来越宽。

实际：5 次回滚中有 4 次伴随 ODD 收缩。最典型的一次：v2.1 上线时 ODD.H 声明覆盖 P=10%—P=95% 的来水范围，运行 4 个月后碰到一次 P=8% 的来水，模型预报误差超出阈值——必须把 ODD 上界收缩到 P=12%，留出更大保守裕度。

**结论**：上线时 ODD 必须保守。"宁可 ODD 范围窄一点，多次扩展，也不要 ODD 范围一开始就大、后来发现要收缩"——后者的修订成本（需要紧急再训 + HIL + 新一轮验证）远超前者。

## 本章小结

本章系统讲述了水利模型从训练完成到生产运行、再到持续迭代的工程链路。七个核心要点：

1. **水利 MLOps ≠ 通用 MLOps**——数据稀缺、物理后果不可逆、ODD 强约束三条根本差异决定了水利场景不能照抄互联网最佳实践。

2. **模型工件必须以四元组绑定**：训练代码哈希 + 数据快照 + 超参数 + 模型权重——四者缺一就失去复现能力。

3. **训练流水线的关键不在自动化程度，而在人工 sanity check 的强度**——水利数据的脏度高于通用场景。

4. **数据集划分严禁简单随机**——必须按时间或洪水事件划分，避免信息泄漏。

5. **金丝雀部署在水利场景慎用**——渠段不能分流。灰度（按站分批）和蓝绿（双环境一键切换）更合适。

6. **在线监控的四个维度**：输入特征漂移、预测分布漂移、性能漂移、ODD 状态。性能漂移因为水文实测滞后，必须用"快指标"作为领先信号。

7. **ODD 收缩比扩展更频繁**——上线时保守，运行中按数据扩展，碰到失败立即收缩。这是水利 MLOps 与通用 MLOps 最反直觉的差异之一。
