> **[管理层速览]**
>
> WorkProxy解决的是一个看似简单但极其关键的工程问题：当调度员或上级系统需要委派一项工作给HydroOS时，如何确保这项工作被完整、可追踪、可验证地执行？
>
> 举个例子：防汛指挥长下达"评估未来48小时淮河流域的防洪风险"这一工作。在传统模式下，这意味着多个电话、多份报告、多次汇报和人工汇总。在HydroOS中，这一工作可以封装为一个WorkProxy——系统自动分解为子任务（降雨预报→水文模拟→水库调度评估→风险区划），分配给多个Agent执行，追踪每个子任务的进度，在汇总后返回一份结构化报告。如果某个子任务失败，WorkProxy自动触发重试或降级预案。
>
> WorkProxy的核心价值在于消除"委派不确定性"：让委派方明确知道工作是否开始、进行到哪一步、是否成功、如果不成功原因是什么。这是从"人委派给人"到"人委派给系统"的工程基础。

## 开篇故事：一份算了一夜的调度方案

[L1 所有读者]

2024年7月，某流域调度中心的值班员小陈在交班时留下了一份未完成的工作：为应对即将到来的强降雨，需要评估三种不同泄洪方案的风险和效益。他预计凌晨3点前能出结果。

凌晨2:30，小陈启动了方案计算。他没有意识到的是，这个"方案计算"不是运行一个程序那么简单——而是需要依次执行五个步骤：降雨情景分析、洪水演进模拟、水库水位预报、下游淹没评估、方案对比排序。五个步骤中，任何一步出错都会导致后续步骤算出的结果失去意义。

凌晨3:15，洪水演进模拟步骤超时退出（因为模型在处理某个复杂河道断面时陷入数值振荡）。等待这个结果的下游淹没评估步骤在3:16报错——"输入数据格式异常"。到凌晨4:00，小陈只拿到了两个步骤的部分结果，不得不手动拼接、补充假设、硬着头皮写了一份带三条"本报告基于不完整计算"免责声明的方案。

事后复盘发现：问题不在于模型不好（五个模型单独运行都很成功），而在于没有一个机制将这些模型调用组织成一个"原子化的工作单元"——要么全部完成并验证，要么在失败时优雅地回退并通知委派方。如果有一个WorkProxy机制，系统应该在小陈启动计算时就显示"预计完成时间3:45"，在洪水演进模拟超时后自动触发"使用简化模型重试"或"标记此步骤结果置信度降级"，而不是让整个工作链断裂。

> **AI解读：** 这个故事揭示了一个在水利信息化中反复出现的模式：系统有很多"能力"（模型、算法、数据接口），但缺少"把能力串起来形成完整工作"的机制。WorkProxy填补的正是这个空白——它不是创造新能力，而是让已有的能力可以被可靠地委派和执行。

## 11.1 WorkProxy的概念与形式化定义 [L1]

### 11.1.1 什么是WorkProxy

**WorkProxy**（工作代理）是将一组Agent-Skill组合及其执行计划封装为一个可委派、可追踪、可回滚的标准化工作单元的平台机制。

关键设计要点：
- **可委派**：委派方（人类操作员或上层系统）只需定义工作目标和约束，不需要指定"怎么做"——WorkProxy自动分解任务并分配执行
- **可追踪**：委派方可以实时查看工作进度——哪些子任务已完成、哪些正在执行、哪些遇到异常
- **可回滚**：当工作执行过程中出现不可恢复的错误时，WorkProxy执行逆向操作栈，将系统恢复到执行前状态（或安全状态）

### 11.1.2 形式化定义

一个WorkProxy被形式化定义为一个七元组：

$$\text{WorkProxy} \triangleq \langle \mathcal{G}, \mathcal{P}, \mathcal{R}, \mathcal{A}, \mathcal{T}, \mathcal{E}, \mathcal{H} \rangle \tag{11-1}$$

其中：
- **$\mathcal{G}$（Goal，工作目标）**：以结构化形式描述的工作产出物要求，如"生成48小时防洪风险评估报告，包含方案对比表"
- **$\mathcal{P}$（Plan，执行计划）**：由Agent Fabric编排引擎生成的DAG，描述子任务的拓扑顺序和依赖关系
- **$\mathcal{R}$（Resources，资源约束）**：执行本工作所需的计算资源预算、时间预算、Agent池约束
- **$\mathcal{A}$（Agents，执行Agent映射）**：将每个子任务映射到具体的Agent实例
- **$\mathcal{T}$（Trace，执行追踪）**：每个子任务的执行状态、起止时间、输入输出的结构化日志
- **$\mathcal{E}$（Exceptions，异常处理策略）**：针对每类可能异常的回退/重试/降级/告警策略
- **$\mathcal{H}$（History，历史记录）**：本WorkProxy实例从创建到完成的全生命周期时间线

### 11.1.3 与邻近概念的对比

**表11-1：WorkProxy与邻近概念的工程区别**

| 概念 | 粒度 | 关注点 | 创建者 | 谁执行 |
|------|------|--------|--------|--------|
| Skill | 单个算法调用 | 输入→计算→输出 | 算法工程师 | L2内核调度引擎 |
| Agent | 持续运行的智能体 | 感知→决策→行动 | 平台管理员 | Agent Fabric |
| WorkProxy | 一个完整工作单元 | 委派→执行→追踪→完成 | 调度员/上层系统 | 多个Agent协同 |
| 微服务 | 持续运行的服务 | 请求→响应 | 开发者 | 容器编排平台 |

关键区别：Skill和Agent是**持续运行的能力单元**，WorkProxy是**一次性（或重复性）的工作实例**。当调度员下达"评估防洪风险"时，创建的是一个WorkProxy实例，该实例在执行过程中调用了多个Skill和Agent，完成工作后销毁（或归档）。

## 11.2 任务分解：从目标到DAG [L2]

### 11.2.1 自动分解策略

WorkProxy的编排引擎接收一个高层目标描述后，通过以下流程自动生成执行计划：

**步骤1 — 目标解析**：将自然语言目标（如"评估淮河流域未来48小时防洪风险"）解析为结构化的目标规格，提取关键参数：时空范围、分析类型、输出要求。

**步骤2 — 能力匹配**：查询Agent注册表（第9章）和Skill注册中心（第3章），匹配能够完成各子任务的Agent和Skill。

**步骤3 — DAG生成**：根据子任务的数据依赖关系构建有向无环图。父任务→子任务的箭头表示"子任务需要父任务的输出作为输入"。

**步骤4 — 资源估算**：根据每个子任务的历史执行数据，估算总计算时间、所需内存和存储空间。

**步骤5 — 计划验证**：检查执行计划是否满足资源约束和时间预算。如果不满足，触发裁剪策略——如降低模拟分辨率、减少方案比选数量、使用简化模型替代。

### 11.2.2 子任务依赖图示例

以"48小时防洪风险评估"WorkProxy为例，生成的DAG如下：

```
降雨预报(《水控》) ──→ 水文模拟(T2) ──→ 水库调度评估(《标治》) ──→ 综合风险报告(T6)
                     ↘                  ↗
                      淹没评估(《平台》) ──→ 方案对比(《算法》) ──→
```

- 《水控》和《平台》可以并行执行（无数据依赖）
- T2等待《水控》完成
- 《标治》等待T2完成
- 《算法》等待《标治》和《平台》都完成
- T6等待《算法》完成

[工程解释] 这个DAG看起来简单，但在实践中有一个重要的工程细节：子任务之间的数据传递不是简单的"等上一个跑完再跑下一个"，而是需要显式的数据契约——上一个子任务的输出schema必须与下一个子任务的输入schema兼容。WorkProxy在执行前会做schema兼容性校验，提前发现"上游输出的是NetCDF但下游要求CSV"这种集成问题，而不是在执行到一半时才报错。

## 11.3 执行追踪与异常处理 [L2]

### 11.3.1 执行状态追踪

WorkProxy的执行追踪系统为每个子任务维护以下状态信息：

**表11-2：子任务执行追踪记录字段**

| 字段 | 说明 | 示例 |
|------|------|------|
| task_id | 子任务唯一ID | T_20240801_003 |
| status | PENDING / QUEUED / RUNNING / COMPLETED / FAILED / CANCELLED | RUNNING |
| assigned_agent | 被分配到的Agent ID | agent_huaihe_forecast_01 |
| started_at | 开始执行时间（ISO 8601） | 2024-08-01T02:30:00Z |
| completed_at | 完成时间（仅COMPLETED/FAILED有值） | 2024-08-01T02:35:42Z |
| progress_pct | Agent汇报的完成百分比 | 67 |
| input_hash | 输入的SHA-256哈希（用于结果缓存命中判断） | a3f2b8... |
| output_summary | 输出的摘要（含数据量、关键指标） | "预测72h径流，RMSE=0.12" |
| error_detail | 错误描述（仅FAILED有值） | "模型数值振荡，断面K18+200" |

所有追踪数据实时同步到L1数据底座，委派方可以通过L4应用Dashboard查看任意时刻的执行状态。

### 11.3.2 异常处理策略

WorkProxy的异常处理不是简单的"重试N次后放弃"。水利场景中的异常有不同性质，需要不同的处理策略：

**可重试异常**：临时性资源不足（内存不够）、通信超时。策略：指数退避重试，最多3次，每次间隔翻倍（30s → 60s → 120s）。

**可降级异常**：复杂模型计算失败。策略：切换到简化模型版本（如从全尺度物理模型降级为机器学习代理模型），结果标注"置信度降级"。

**可跳过异常**：非关键子任务失败（如生成报告中的某个辅助图表）。策略：跳过该子任务，在最终结果中标注"部分内容缺失"。

**阻塞性异常**：关键子任务失败且无降级方案。策略：中止整个WorkProxy，执行回滚，通知委派方并提供已完成的中间结果。

**安全相关异常**：子任务执行过程中触发安全包络（ODD越界、安全裕度不足）。策略：立即中止所有子任务，切换到安全状态，通知人类操作员。

### 11.3.3 回滚机制

对于涉及写操作（如修改了数据库、下发了控制指令）的WorkProxy，异常中止时需要执行回滚。WorkProxy维护一个"逆向操作栈"——按执行的逆序记录每个步骤的补偿操作。

例如，一个WorkProxy先更新了数据库中的调度方案（写操作），然后尝试运行模型（计算操作），模型失败了。回滚操作是：撤销数据库中的调度方案更新（将其恢复为执行前版本）。对于已经下发到物理设备的控制指令，回滚操作是：下发"恢复原状"的指令序列——这需要确保物理系统在回滚过程中不跨越安全边界。

## 11.4 WorkProxy的委派模式 [L2]

### 11.4.1 三种委派触发方式

**人工委派**：人类调度员通过L4应用界面创建WorkProxy，填写工作目标和参数，点击提交。这是最常见的模式——防汛指挥长的"帮我评估一下"、水资源管理者的"生成下周供水计划"。

**定时委派**：在Cron调度中预设WorkProxy模板，到时间自动触发执行。例如，每天凌晨3:00自动执行"24小时流域水情评估"WorkProxy。

**事件驱动委派**：由系统事件触发，如ODD越界告警→自动创建"ODD越界影响评估"WorkProxy、传感器故障→自动创建"传感器故障影响范围分析"WorkProxy。

### 11.4.2 执行透明度：委派方的信息权利

委派方在WorkProxy执行过程中享有以下信息权利：

- **进度可见性**：任意时刻可以看到DAG中每个子任务的状态
- **中间结果可查看**：已完成的子任务输出可提前查看（在最终汇总之前）
- **异常及时通知**：任何子任务失败都会在30秒内通知委派方
- **干预权**：委派方可以随时暂停、修改参数后继续、或取消WorkProxy
- **追溯权**：WorkProxy完成后，所有执行追踪记录保留N天（默认90天），可供审计和复盘

## 11.5 WorkProxy与HydroOS各层的集成 [L2]

### 11.5.1 系统集成架构

WorkProxy在HydroOS中的集成位置：

- **L4应用层**：提供WorkProxy的创建界面（WorkProxy模板库、参数配置向导）、监控Dashboard（DAG可视化、实时进度条）和历史查询界面
- **L3服务层**：WorkProxy编排引擎驻留在此层，与Agent Fabric、Skill注册中心、事件总线交互
- **L2内核层**：WorkProxy的DAG执行为每个子任务申请计算资源，通过L2调度引擎分配
- **L1数据底座**：WorkProxy的执行追踪日志写入时序数据库，中间结果存储在对象存储中

### 11.5.2 与四预闭环的关系

WorkProxy是四预闭环在批量任务层面的平台化实现。一个典型的防汛四预流程可以表达为一个WorkProxy模板：

1. 预报步骤 = WorkProxy子任务"气象水文耦合预报"
2. 预警步骤 = WorkProxy子任务"ODD状态评估与预警生成"
3. 预演步骤 = WorkProxy子任务"多方案仿真对比"
4. 预案步骤 = WorkProxy子任务"预案生成与审批推送"

通过WorkProxy的编排，四预从一个需要人工串联的过程，变成了一个可一键触发、自动流转、全程追踪的标准化工作流。
